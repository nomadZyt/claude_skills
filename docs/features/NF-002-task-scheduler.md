NF-002: 多任务并发调度器 Skill

状态：In Progress       优先级：High
工作量：Large  影响：提供自动化的多任务并发管理能力，大幅提升批量需求的开发效率

## 问题
**当前痛点：**
- 用户有多个开发需求（任务清单），需要手动逐个创建 NF 并管理
- 无法充分利用 Claude 的并发能力，串行处理效率低
- 需要人工监控多个 Agent 的执行状态
- 任务数量多时，容易遗漏或重复

**目标：**
创建一个智能任务调度器 Skill，能够：
1. 从任务清单文件读取多个需求
2. 为每个需求自动创建对应的 NF 并分配 Agent
3. 控制并发数量（最多 4 个 Agent 同时执行）
4. 使用 `/loop` 定期检查所有 Agent 的 NF 状态
5. 自动调度：当有 Agent 完成时，启动下一个待处理任务
6. 提供实时进度报告和最终汇总

## 方案

### 核心架构
```
任务清单文件 (tasks.md)
    ↓
任务调度器 Skill (/task-scheduler)
    ↓
├─ 解析任务清单
├─ 为每个任务创建 NF (调用 /nf-new)
├─ 维护任务队列（待处理/进行中/已完成）
├─ Agent 池管理（最多 4 个并发）
└─ 循环监控 (使用 /loop + /nf-status)
    ↓
自动调度逻辑
```

### 实现步骤

#### 1. 任务清单文件格式设计
文件路径：`docs/tasks/task-list.md`
```markdown
# 任务清单

## 待处理
- [ ] 任务1：添加深色模式切换功能 [优先级:High] [工作量:Medium]
- [ ] 任务2：优化项目分析器性能 [优先级:Medium] [工作量:Large]
- [ ] 任务3：修复 tmux 集成问题 [优先级:Low] [工作量:Small]

## 进行中
（由调度器自动更新）

## 已完成
（由调度器自动更新）
```

#### 2. Skill 文件结构
创建 `task-scheduler/SKILL.md`，包含：
- 任务解析器：读取并解析 task-list.md
- NF 创建器：调用 `/nf-new` 为每个任务创建 NF
- Agent 管理器：
  - 维护 Agent 池（agent_id → NF 映射）
  - 控制并发数 ≤ 4
  - 启动新 Agent（使用 Agent tool）
- 状态监控器：
  - 使用 `/loop` + `/nf-status` 定期检查
  - 解析 NF 状态变化
- 调度逻辑：
  - 当 Agent 完成（NF 状态 → Complete）时
  - 从待处理队列取下一个任务
  - 启动新 Agent

#### 3. 关键技术决策

**并发控制：**
- 使用队列结构：`pending_queue`, `running_agents`, `completed_tasks`
- 每次循环检查：`len(running_agents) < 4` 则启动新任务

**状态同步：**
- 使用 `/loop 5m` 每 5 分钟检查一次 NF 状态
- 解析 FEATURE_INDEX.md 获取所有 NF 的最新状态
- 更新 running_agents 列表

**Agent 通信：**
- 每个 Agent 独立运行，通过 NF 文件通信
- 调度器只读取 NF 状态，不直接控制 Agent

**错误处理：**
- Agent 失败：标记任务为 Failed，记录日志
- 状态检查超时：重试 3 次后标记异常
- 任务清单格式错误：验证并提示用户修复

#### 4. 数据流
```
[解析 task-list.md]
    ↓
[为每个任务调用 /nf-new 创建 NF-XXX]
    ↓
[建立映射: Task → NF-XXX → Agent-ID]
    ↓
[启动前 4 个 Agent]
    ↓
[/loop 5m: 检查 NF 状态]
    ↓
[检测到 Complete → 启动新 Agent]
    ↓
[所有任务完成 → 生成报告]
```

### 考虑过的替代方案

1. **方案 A：使用 TeamCreate + TaskList**
   - 优点：利用内置的团队协作机制
   - 缺点：
     - TeamCreate 适合单个大型任务的分解，不适合多个独立任务
     - TaskList 没有任务清单文件的持久化
     - 不支持从外部文件导入任务
   - 不选原因：不符合"从任务清单文件读取"的需求

2. **方案 B：手动管理 + Cron**
   - 优点：简单直接
   - 缺点：
     - 用户需要手动创建每个 NF
     - 无法自动调度和并发控制
     - 需要人工监控
   - 不选原因：没有自动化优势

3. **方案 C：纯 Shell 脚本**
   - 优点：轻量，容易调试
   - 缺点：
     - 无法调用 Claude Agent
     - 无法使用 /nf-system 命令
     - 需要手动实现状态解析
   - 不选原因：无法与 Claude 集成

## 备注

**技术债务：**
1. 初版可能不支持任务优先级排序，先按顺序执行
2. Agent 失败重试机制需要在后续版本完善
3. 任务依赖关系（Task A 依赖 Task B）暂不支持

**后续优化点：**
1. 添加任务优先级队列（High 优先执行）
2. 支持任务依赖关系（DAG 调度）
3. 实时 Web UI 显示进度（可选）
4. 支持暂停/恢复/取消任务
5. 导出调度报告（Markdown/JSON）
6. 集成通知服务（Slack/Email）

**设计考虑：**
- 调度器本身应该是轻量的，不阻塞用户操作
- 使用 /loop 而不是阻塞式等待，保持 REPL 可用
- 所有状态持久化在文件中，避免内存状态丢失
- 设计为可扩展的插件式架构

**安全考虑：**
- 任务清单文件应该被 gitignore（可能包含敏感信息）
- Agent 执行的代码应该经过用户审核
- 并发数限制防止资源耗尽
