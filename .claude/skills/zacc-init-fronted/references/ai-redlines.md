# AI 红线规则识别方法

> 供 zacc-init-fronted 步骤 5 使用，基于步骤 1-4 的分析结果自动提取红线规则。

## 提取逻辑

红线不是凭空定义的，而是从项目现有代码和配置中**推导**出来的。每类红线都有明确的信息来源。

---

## 1. 技术栈红线提取

**信息来源**：步骤 1（项目信息收集）

### 依赖白名单
- 读取 `package.json` 的 `dependencies` 和 `devDependencies`
- 所有已声明的依赖构成"允许使用"的白名单
- 新代码中 import 的包必须在此白名单内，否则需要用户确认

### 构建配置锁定
- 识别到的构建工具配置文件（如 `vite.config.ts`）标记为不可修改
- 构建相关的 package.json scripts 标记为不可修改

### 包管理器锁定
- 从 lock 文件判断的包管理器，不可更换
- 安装依赖必须使用对应命令（npm install / yarn add / pnpm add）

### TypeScript 配置锁定
- `tsconfig.json` 的 `strict`、`target`、`module` 等核心配置不可修改
- `paths` 别名配置不可修改

---

## 2. 架构模式红线提取

**信息来源**：步骤 2（项目结构分析）+ 步骤 4（数据流转分析）

### 目录规范提取

从项目结构分析结果中提取：

```
规则模板：
- 页面文件必须放在：{识别到的 pages/views 目录}
- 组件文件必须放在：{识别到的 components 目录}
- API 定义必须放在：{识别到的 api/services 目录}
- 状态管理必须放在：{识别到的 store/stores 目录}
- 工具函数必须放在：{识别到的 utils/helpers 目录}
- 自定义 Hooks 必须放在：{识别到的 hooks 目录}
- 样式文件必须放在：{识别到的 styles 目录或与组件同目录}
- 类型定义必须放在：{识别到的 types/typings 目录}
```

### 分层规范提取

从数据流转分析中提取：

- **API 调用规范**：如果项目有统一的请求封装（如 `utils/request.ts`），则所有 API 调用必须通过该封装，不得直接使用 axios/fetch
- **状态管理规范**：如果项目使用 Pinia/Redux/Zustand 等，新功能必须使用相同方案，不得引入其他状态管理库
- **组件组织规范**：如果项目按功能组织组件（feature-based），新组件必须遵循相同模式

### 模块边界提取

如果项目有清晰的模块划分：
- 模块间通信必须通过约定的方式（Store/事件总线/props）
- 不得直接引用其他模块的内部文件

---

## 3. 代码风格红线提取

**信息来源**：步骤 3（代码规范提取）

### 从 ESLint 配置提取
- 关键规则（如 `no-var`, `prefer-const`, `no-unused-vars`）
- 自定义规则（项目特有的 lint 规则）
- extends 配置（使用了哪些规则集）

### 从 Prettier 配置提取
- 缩进（`tabWidth`, `useTabs`）
- 引号（`singleQuote`）
- 分号（`semi`）
- 行宽（`printWidth`）
- 尾逗号（`trailingComma`）

### 从代码采样推断
- 文件命名规则（从 3-5 个典型文件推断）
- 组件命名规则
- 变量/函数命名规则
- CSS 类名规则（BEM / camelCase / 与 CSS Modules 对应）

### 从 CSS 方案推断
- 如果项目使用 CSS Modules → 新样式必须用 CSS Modules
- 如果项目使用 Tailwind → 优先使用 Tailwind 类名
- 如果项目使用 Less/Sass → 新样式必须用相同预处理器

---

## 4. 业务逻辑红线提取

**信息来源**：步骤 4（数据流转 + 页面流转分析）

### 数据流转红线

从数据流转分析中提取必须遵循的层级：

```
识别项目的数据流转模式，例如：
- 路由参数 → 页面组件 → 调用 API 方法 → Store 更新 → 组件响应式更新
- 如果项目所有 API 都通过 Store action 调用，那么新功能也必须如此
- 如果项目有统一的请求/响应拦截器，不得绕过
```

### 页面流转红线

从页面流转分析中提取：
- 不得修改已有页面的路由路径（可能影响外部链接/书签）
- 路由参数传递方式必须与现有模式一致（如果项目用 query，新页面也用 query）
- 新页面必须注册到路由配置中（不得用 window.location 跳转）

### 拦截器/中间件红线

如果项目有以下机制，不得绕过：
- 请求拦截器（Token 注入、请求签名等）
- 响应拦截器（错误码处理、Token 刷新等）
- 路由守卫（权限检查、登录检查等）

---

## 5. 功能修改确认规则

以下操作在执行前必须使用 AskUserQuestion 弹窗确认：

| 操作类型 | 原因 | 确认提示模板 |
|---------|------|-------------|
| 修改组件 props/接口 | 可能影响所有调用方 | "即将修改 {组件名} 的 props 定义，这会影响 {N} 处调用。确认修改？" |
| 修改路由配置 | 可能影响外部链接和导航 | "即将修改路由 {路径}，这可能影响已有的页面跳转。确认修改？" |
| 修改 Store 结构 | 可能影响所有消费者 | "即将修改 {Store名} 的结构，这会影响 {N} 个组件。确认修改？" |
| 修改 API 逻辑 | 可能影响请求行为 | "即将修改 {API文件} 的请求/响应处理逻辑。确认修改？" |
| 删除/重命名文件 | 不可逆操作 | "即将{删除/重命名} {文件路径}。确认操作？" |
| 修改公共工具函数 | 可能影响所有调用方 | "即将修改公共函数 {函数名}，有 {N} 处调用。确认修改？" |

---

## 输出到 AI_RULES.md

将提取到的红线规则填入 `templates/AI_RULES.md.tpl` 模板的对应章节。

注意：
- 每条红线必须是具体的、可执行的（不要写"遵循最佳实践"这种模糊规则）
- 每条红线最好引用具体的文件路径或配置项
- 如果某个类别没有识别到明确的规则，写"暂无明确规则，遵循项目现有模式"
